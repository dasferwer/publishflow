# Ограничение демонстрационного журнала article-events

Очередь `publishflow.article-events` не имеет встроенного потребителя: это события
для будущих интеграций. Retention — отдельная, явно включаемая оператором политика
демонстрации. По умолчанию срок пустой, publisher не устанавливает policy и не
удаляет outbox. Внешний consumer или гарантия доставки ему здесь не реализованы.

## Предпросмотр и включение

Сначала запустите обычный стек. Выберите срок и допустимый объём событий, например
7 дней и 10 MiB тел сообщений. Значения в примере — технический пример, а не
обязательный бизнес-срок хранения.

```bash
# Читает один пакет outbox и печатает план policy; никаких записей/запросов к брокеру.
docker compose run --rm --no-deps --entrypoint python \
  -e PUBLISHFLOW_ARTICLE_RETENTION_SECONDS=604800 \
  api -m publishflow.retention --dry-run

# Та же операция с фиксированным временем воспроизводит SQL cutoff и порядок ID.
docker compose run --rm --no-deps --entrypoint python \
  -e PUBLISHFLOW_ARTICLE_RETENTION_SECONDS=604800 \
  api -m publishflow.retention --dry-run --now 2026-10-09T12:00:00+00:00

# Устанавливает policy брокера и удаляет только один SQL-пакет.
docker compose run --rm --no-deps --entrypoint python \
  -e PUBLISHFLOW_ARTICLE_RETENTION_SECONDS=604800 \
  -e PUBLISHFLOW_ARTICLE_QUEUE_MAX_BYTES=10485760 \
  -e PUBLISHFLOW_ARTICLE_RETENTION_BATCH_SIZE=1000 \
  api -m publishflow.retention --apply
```

Предпросмотр содержит `cutoff`, определение policy, `event_ids` и `count`.
`count` относится к одному пакету, а не всему backlog. `--now` требует часовой пояс;
по умолчанию время UTC берётся один раз при старте команды. Для неизменившейся БД
предпросмотр детерминирован: `published_at`, затем UUID. При конкуренции `--apply`
может выбрать другой пакет, поскольку пропускает занятые строки.

Повторяйте `--apply` для следующих пакетов; оператор может запускать команду
периодически через свой планировщик. Встроенного автоматического SQL-cleaner нет.
TTL и лимит очереди действуют постоянно после первого успешного применения.

## Что удаляется

| Хранилище | Условие | Граница |
|---|---|---|
| PostgreSQL `outbox_events` | Только `article.*`, `published_at < now - срок` | Один пакет 1–10000 строк, по умолчанию 1000 |
| RabbitMQ `publishflow.article-events` | `message-ttl = срок × 1000` и `max-length-bytes` | При TTL сообщение теряет доступность; при переполнении удаляются самые ранние ready-сообщения (`drop-head`) |

Неопубликованные события (`published_at IS NULL`), недавно подтверждённые события
и событие ровно на cutoff сохраняются. Возраст SQL отсчитывается от подтверждения
брокером, а не создания: старое событие после длительного простоя publisher получает
полный срок хранения. Все импортные события, задания/checkpoint, `article_history`,
тексты версий и состояние публикации остаются в БД. Неопубликованный backlog может
расти без ограничения: retention не заменяет устранение отказа publisher.

Удаление SQL выполняется в транзакции с `FOR UPDATE SKIP LOCKED`; два cleaner не
забирают одну строку, занятая строка остаётся до следующего запуска. Ошибка/откат
транзакции сохраняет строки. Уже подтверждённые события повторно не публикуются.
После удаления outbox/очереди replay этих событий больше невозможен; тексты и
редакционная история при этом сохраняются. Брокерный confirm означает принятие
брокером, а не обработку внешней интеграцией.

Для RabbitMQ срок отсчитывается от поступления в очередь, а лимит байтов учитывает
только тела ready-сообщений. Это не предел всего диска, метаданных или unacked.
Крупное сообщение может быть удалено целиком даже при успешном confirm. В текущем
стеке consumer отсутствует; при его добавлении надо пересмотреть эту политику.
При включении на существующей очереди старые сообщения могут оставаться доступными:
локальный runtime показал такой backlog после установки TTL 1 с. TTL новых сообщений
проверен отдельно; CLI не обещает немедленную возрастную очистку старого backlog.
Освобождение физических ресурсов также может запаздывать. Лимит байтов ограничивает
ready payload, в том числе при применении policy к уже накопленной очереди.
Дубликаты занимают тот же бюджет. Импортные и invalid-очереди policy не затрагивает.

Policy `publishflow-article-retention` имеет точный шаблон
`^publishflow\.article-events$`, `apply-to=queues`, priority 100. Она применяется
динамически к существующей очереди без её удаления и без изменения AMQP declaration.
Команда читает определения policies и отказывается заменять совпадающую policy
с другим именем (независимо от priority) или policy с тем
же именем, но другой областью действия. Не меняйте policies одновременно с CLI;
проверяйте эффективную policy в RabbitMQ Management; статистика очереди после PUT
может обновляться с задержкой. Operator policies/queue arguments
могут задавать более строгие лимиты. Нестандартные комбинации broker policies здесь
не объявляются поддержанной внешней интеграцией.

Management API использует `PUBLISHFLOW_RABBITMQ_MANAGEMENT_URL`; имя пользователя,
пароль и vhost берутся из `PUBLISHFLOW_RABBITMQ_URL`. Нужны management plugin и права
на policies. В Compose оба брокера используют management image. За пределами
локального стека используйте HTTPS. CLI не печатает URL и пароли при ошибке.

Брокерная policy и SQL не входят в общую транзакцию. Команда сначала устанавливает
policy; при отказе Management API SQL не удаляется. Если SQL позднее откажет, policy
уже останется включённой. Успешный dry-run не обещает конкретное количество
удалённых брокером сообщений: их возраст и конкуренция в RabbitMQ независимы от SQL.

## Отключение

Пустой срок предотвращает следующие SQL-запуски, но **не удаляет существующую policy**.
Отключите её явно:

```bash
docker compose run --rm --no-deps --entrypoint python \
  api -m publishflow.retention --remove-policy
```

Команда снимает только свою policy, не очищает очередь и не восстанавливает удалённое.
Повторное снятие отсутствующей policy допустимо. Если ранее были другие policies,
они могут снова стать эффективными. Затем удалите срок из операторской конфигурации.

## Проверка

`tests/test_retention.py` выполняется в штатном тестовом профиле с реальными
PostgreSQL и RabbitMQ. Проверяются границы cutoff, пакет из одной строки,
неопубликованные/импортные события, lock/rollback, dry-run без изменения БД/policy,
CLI apply/remove, отказ API до удаления, чужая область и конфликт policy
при устаревшей статистике очереди, TTL и `drop-head`
(три тела по 10 байт при лимите 20: доступны только второе и третье). Импортное
сообщение сохраняется после TTL article-очереди. Это функциональная проверка
локального стенда, а не промышленная гарантия диска, HA или SLA.

[Фактический локальный прогон](verification-retention.md) содержит результаты
и наблюдение для legacy backlog.

Семантика сверена с документацией RabbitMQ:
[TTL](https://www.rabbitmq.com/docs/ttl),
[лимиты очереди](https://www.rabbitmq.com/docs/4.1/maxlength),
[Management HTTP API](https://www.rabbitmq.com/docs/http-api-reference).
