# Проверка retention 09.10.2026

Локальный изолированный стенд: Python 3.12.13, PostgreSQL 17.11,
RabbitMQ 4.3.5, Docker Engine 29.7.2. Проверена рабочая версия на базе
`977906a839be9f75ed2fb750adbf9c2bb71e4206` с изменениями retention.

- Полный `pytest`: **68 passed**, 18,48 с (15 случаев retention).
- Ruff format/check: успешно; mypy: 18 исходных файлов без ошибок.
- Отдельный fixture safety: 38 passed; test-image entrypoint safety: 2 passed.
- `scripts/check_migration.py`: downgrade/upgrade сохранили бизнес-данные.
- Runtime API и три worker запущены в собственном Compose-проекте; `/health` вернул ok.
- Через HTTP создана, согласована и опубликована статья; publisher подтвердил 4 события.
- После тестового старения `published_at` этих четырёх событий предпросмотр показал
  2 кандидата, три применения удалили **2, 2, 0** строк. Pending-событие и импортное
  событие сохранились. Публичный текст и список версий совпали до и после очистки.
- Лимит 20 байт применён к существующей очереди с тремя телами по 10 байт:
  первый элемент удалён, второй и третий доступны. Новое сообщение после policy
  TTL 1 с перестало доставляться после 1,2 с.
- При включении TTL на существующей очереди legacy-сообщения оставались доступны.
  Поэтому быстрый возрастной purge старого backlog не обещается; ограничение ready
  payload и TTL новых сообщений проверены отдельно.

Предварительные неуспешные прогоны не скрыты: отсутствие retention подтвердилось
11 красными тестами; scope/conflict проверки сначала не отказывали чужой policy.
Один ранний полный прогон пересёкся с отдельным тестом на том же собственном стенде
и дал 2 ошибки; последующий последовательный прогон выявил устаревшую статистику
queue-policy. Проверка конфликтов переведена на определения policies. Финальные
68 тестов исполнены последовательно, после исправлений. Первое runtime-ожидание
немедленного опустошения legacy backlog также не выполнилось; семантика в
[инструкции](retention.md) исправлена по фактическому наблюдению.
